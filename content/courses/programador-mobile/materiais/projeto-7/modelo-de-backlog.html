Modelo de backlog

O backlog é a lista do que a equipe vai fazer, da coisa mais importante para a menos. No projeto integrador, ele mora nas Issues do repositório da equipe: uma issue para cada história.

Quem faz o quê

Cada pessoa fica com uma tela, um componente seu e uma tarefa da equipe. Na equipe de 3, alguém fica com duas tarefas e a tela 4 fica de fora. O que você digita aqui fica só neste navegador: imprima ou copie para o README.

Uma história, em três partes

Uma história de usuário descreve o que uma pessoa quer fazer no app, não uma tela. Ela cabe numa frase: Como quem, quero o quê, para quê. O "para quê" ajuda a equipe a decidir os detalhes.

Embaixo dela, o Pronto quando: a lista do que qualquer pessoa da equipe confere no celular para dizer que a história ficou pronta. Use os números dos dados do kit.

a descrição da issue
**História:** Como cliente, quero ver os horários livres do dia,
para marcar sem ligar para o salão.

**Pronto quando:**
- [ ] Na segunda, aparecem 6 horários: o 10:00 e o 14:00 já estão ocupados
- [ ] Na quarta, aparecem 7: o 09:00 está ocupado
- [ ] Sem escolher o dia, aparece "Escolha o dia" embaixo das opções

**Tela:** Agendar (app/agendar/[id].js)

O - [ ] vira uma caixinha no GitHub: quem testa marca cada item atendido. O título da issue é curto e começa por verbo: "Ver os horários livres do dia".

Pronto quando que dá para conferir

Os rótulos de prioridade

Pense numa festa com pouco dinheiro: o bolo precisa ter; os docinhos deveriam ter; o mágico, só se sobrar dinheiro; os fogos ficam de fora. No backlog é igual. É o MoSCoW, das iniciais em inglês de must, should, could e won't.

RótuloQuer dizerQuando entra
precisa-tersem isso, não há appE42 e E43
deveria-terimportante, mas a apresentação vive semE43 e E44
poderia-tersó se sobrar tempoE44, se der
(sem issue)não vai ter desta vezno README, em "Fora desta versão"

Se tudo é precisa-ter, nada é prioridade: o que não cabe em cinco encontros vai para baixo.

No GitHub

Os rótulos (uma pessoa, uma vez)

  • No repositório da equipe, aba Issues, botão Labels
  • New label, o nome precisa-ter e Create label. Repita para deveria-ter e poderia-ter

Uma issue (cada pessoa, para a sua tela)

  • Aba Issues, botão New issue
  • O título curto, com verbo, e a descrição com a história e o Pronto quando (o modelo acima)
  • À direita: em Assignees, você; em Labels, o rótulo
  • Create. A issue ganha um número, como #4: no E42, o pull request da tela diz Closes #4 e fecha a issue sozinho no merge

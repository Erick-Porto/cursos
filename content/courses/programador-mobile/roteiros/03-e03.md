## Visão do encontro

**Objetivo:** o `lojinha-regras` ganha histórico e vai para o GitHub, e daqui em diante toda mudança chega à `main` por branch, Pull Request e revisão. No Bloco 1, o Git do zero (`init`, `.gitignore`, `add`, `commit`, `push`) e o fluxo de equipe (branch, PR, revisão, conflito). No Bloco 2, as ferramentas de qualidade: ESLint, Prettier, EditorConfig e o depurador do VS Code. No bloco Projeto, o `racha-conta` faz o mesmo caminho: etapa 2 do Projeto 1.

**Como os slides foram escritos:** para quem nunca programou. Cada palavra nova é explicada na hora (há um slide "Palavras novas de hoje" em cada aula), toda mensagem do Git em inglês vem traduzida, e os comandos novos têm uma tabela "em português". Em aula, leia a tradução em voz alta e não vá além dela: o `if`, o `filter`, o `toLowerCase` e a função `somar` aparecem só para leitura e têm encontro próprio (E06, E07 e E09).

**Slides de seção:** cada conceito vem em três slides. O primeiro, a seção, tem só o nome do conceito e uma frase de gancho, no centro ("O repositório" e "Onde você guarda as fotos de uma viagem para achar depois?"). É a hora da conversa: leia o gancho, ouça duas ou três respostas e explique com a analogia indicada abaixo. O segundo, a âncora, explica o que é e como usar, por escrito e completo; em aula, passe por ele apontando o que acabou de dizer, sem ler tudo. O terceiro, "... na prática", mostra dois ou três casos de uso com a saída real: quase todos coincidem com uma demonstração deste roteiro, indicada em cada seção. As analogias do encontro andam juntas, e são sempre as mesmas: o repositório é o álbum de fotos do projeto, o commit é a foto com legenda, o GitHub é o álbum na nuvem, a branch é o rascunho paralelo, o Pull Request é pedir a um colega que revise antes de juntar; o linter é o corretor ortográfico do código, o Prettier é a norma de formatação de um trabalho escolar, e o depurador é a câmera lenta com pausa.

**Resultado ao fim das 4h:** cada aluno tem o `lojinha-regras` público no GitHub, com `.gitignore`; a Issue #1 ("Relatório com categoria em maiúscula mostra R$ NaN") provada com um breakpoint condicional e fechada por um PR revisado; o PR `chore/qualidade` com `eslint.config.js`, os scripts `lint` e `formatar`, `.prettierrc`, `.prettierignore`, `.editorconfig` e `.vscode/settings.json`, com `npm run lint` e `npx prettier --check .` limpos. O `racha-conta` com o commit da etapa 1 e, no GitHub, público; README, ESLint e Prettier terminam em casa, no commit da etapa 2. O conflito em dupla do laboratório vai para a tarefa de casa.

**Pré-requisitos:** do E01, o Git instalado e configurado (`user.name`, `user.email` e `init.defaultBranch main`), a conta no GitHub e as extensões Prettier, ESLint e Error Lens. Do E02, o `lojinha-regras` com `src/data/produtos.js`, `src/data/catalogo.json`, os scripts `catalogo` e `relatorio`, o `picocolors` instalado e a anotação da tarefa: `npm run relatorio Audio` mostra `Produtos: 0` e `Preço médio: R$ NaN`. A turma nunca fez um commit.

**Materiais:** projetor, Wi-Fi, quadro com duas cores, uma segunda conta do GitHub (ou um aluno voluntário) num segundo navegador, quiz publicado.

## Bloco 1 · Git e GitHub (60 min)

**"O que você vai aprender", "Palavras novas de hoje" e "Um projeto, dois problemas" (3 min).** Leia as seis palavras novas em voz alta, uma frase cada. Depois, a história e a pergunta. Anote as respostas num canto do quadro ("salvar na nuvem", "cada um na sua cópia") e não corrija: elas voltam no fechamento do bloco.

Da seção "O repositório" à seção "O GitHub", é mão na massa (22 minutos ao todo): a turma faz junto, cada um no próprio `lojinha-regras`. Você projeta o terminal da demonstração e só avança quando a maioria tiver o mesmo resultado. Cada seção abre com o gancho do slide, que é a pergunta para a turma.

**Seção "O repositório" (5 min).** Pergunte, com o gancho: "onde vocês guardam as fotos de uma viagem para achar depois?". Esperado: num álbum, numa pasta do celular. "O repositório é o álbum do projeto: cada commit é uma foto de todos os arquivos naquele momento." Em "O primeiro repositório":

:::steps
1. `cd lojinha-regras`, `git init` e `git status`. Leia a lista em voz alta, com a tradução do slide (*No commits yet*, *Untracked files*), e aponte o `node_modules/`: "isso vai para o GitHub?". Esperado: não; o `npm install` recria.
:::

Em "O repositório na prática", aponte o caso 1 (`fatal: not a git repository`): é o que aparece para quem abriu o terminal fora da pasta. O caso 3 volta no bloco Projeto.

**Seção "O .gitignore" (4 min).** Pergunte, com o gancho: "na foto do quarto que vocês mandam para alguém, o que fica fora?". Esperado: a bagunça, o que não interessa. "O `.gitignore` é a lista do que não entra nas fotos."

:::steps
2. No VS Code, **New File** na raiz: `.gitignore`, com `node_modules/`. Salve e rode `git status`: a pasta sumiu e o `.gitignore` apareceu.
:::

Em "O .gitignore na prática", avise do caso 2: no PowerShell, o `echo` grava o arquivo em UTF-16, e o Git não o lê. O caso 3, o `git rm -r --cached`, volta no "Pense" do PR.

**Seção "Commits" (7 min).** Pergunte, com o gancho: "numa foto de grupo, o que acontece antes do clique?". Esperado: alguém chama quem vai sair na foto. "O `git add` chama os arquivos para a foto; o `git commit` clica e escreve a legenda."

:::steps
3. Projete "add e commit: a fotografia" e percorra o diagrama com o dedo: as duas primeiras setas são o que a turma vai fazer agora.
4. `git add .` e `git status`: tudo em *Changes to be committed*. Mostre a linha correspondente em "Lendo o git status".
5. `git commit -m "E03: projeto lojinha-regras"` e `git log --oneline`. Em "O primeiro commit", leia a tabela e aponte o `HEAD -> main`: "vocês estão aqui". Quem receber `Author identity unknown` refaz os dois `git config --global` do E01.
6. "Commits na prática": rode `git status` de novo e mostre o *nothing to commit, working tree clean* do caso 3. Aponte os casos 1 e 2 sem demonstrar.
7. "Mensagens de commit": "a mensagem é a legenda da foto". Peça a versão boa de cada mensagem ruim antes de mostrar a coluna da direita.
:::

**Seção "O GitHub" (6 min).** Pergunte, com o gancho: "se o seu celular cair na água hoje, o que acontece com as fotos?". Esperado: quem tem cópia na nuvem não perde nada. "O GitHub é o álbum guardado na nuvem. O push manda a sua cópia para lá; o pull traz a de lá."

:::steps
8. No GitHub, **New repository**: `lojinha-regras`, **Public**, sem README e sem `.gitignore`. Copie os três comandos de *push an existing repository* e leia "Os três comandos em português" antes de rodar; no primeiro `git push`, o navegador abre para autorizar.
9. Atualize a página: arquivos e commit, sem `node_modules/`. Clique no commit e mostre o que entrou.
:::

Em "O GitHub na prática", ligue o caso 2 à história do começo: "o notebook da Ana não liga, e o `git clone` traz tudo de volta". O `git clone` reaparece na revisão de código.

Marco: às 0:35, todos com o commit no GitHub. Quem travar no login segue com o commit local e envia na pausa; o repositório público é pré-requisito do E04.

**"Pense" do `git status` (4 min).** Individual, 2 minutos. Esperado: só o `produtos.js` entra, com uma mensagem que nem fala dele. Pergunte: "como deixar os dois assuntos em commits separados?". Esperado: commit da descrição primeiro; depois `git add` do `package.json` e do script.

**Seção "Branches" (6 min).** Pergunte, com o gancho: "vocês escrevem a redação direto na folha que vai ser entregue?". Esperado: não, primeiro num rascunho. "A branch é o rascunho paralelo: dá para testar sem estragar a versão boa, a `main`. O merge passa o rascunho a limpo." Ao vivo, no repositório que você acabou de criar, os dois casos de "Branches na prática":

:::steps
1. `git switch -c chore/readme` e `git branch`: o `*` marca onde você está.
2. Crie `README.md` com o título e uma seção "Comandos" (`npm install`, `npm run catalogo`, `npm run relatorio audio`). Commit "Cria o README com os comandos".
3. `git switch main`: o README some da pasta diante da turma. Volte para a branch e ele reaparece.
4. `git log --oneline --graph --all`: a branch um commit à frente da `main`.
:::

Não faça o merge local: ele vai pelo PR. Leia no slide "Merge: juntando à main" o grafo e o aviso do editor; se alguém já caiu no Vim, `:wq` e <kbd>Enter</kbd>.

**Seção "Issues" (3 min).** Pergunte, com o gancho: "na assistência técnica, o que vocês recebem quando deixam o celular quebrado?". Esperado: um número de protocolo e a descrição do defeito. "A Issue é o chamado do repositório: número, o que aconteceu e quem resolve."

:::steps
1. Aba **Issues**, **New issue**: a Issue do slide, com Passos, Esperado e Obtido. Mostre o `#1`. "Quem vai corrigir são vocês, no laboratório."
:::

Em "Issues na prática", leia só o caso 3: o `Closes #1` fecha a Issue no merge, e é o que o laboratório pede.

**Seção "Pull Request" (8 min).** Pergunte, com o gancho: "antes de entregar um trabalho em grupo, por que pedir para um colega ler?". Esperado: ele acha o que você não viu. "O Pull Request é isso: pedir para um colega revisar antes de juntar." Ao vivo, com o README, que segue o caminho de "Pull Request na prática":

:::steps
2. **Settings**, **Collaborators**, **Add people**: a segunda conta. No outro navegador, aceite o convite em github.com/notifications.
3. `git push -u origin chore/readme`, **Compare & pull request**, descrição com "O que muda" e "Como testar"; a segunda conta em **Reviewers**.
4. Com a segunda conta, em **Files changed**, comente a linha dos comandos: "falta dizer que o `npm install` vem antes". Envie com **Request changes**. Aponte a tabela de "Revisão de código", com a tradução de cada opção.
5. Atenda com um commit na mesma branch e `git push`: o PR se atualiza sozinho (o caso 2 do slide). Aprove com a segunda conta.
6. **Merge pull request**, **Delete branch**; no terminal, `git switch main`, `git pull` e `git branch -d chore/readme` (o caso 3).
:::

Em "O que conferir na revisão", a frase que fica: "nunca aprove sem rodar". Em "Da branch à main", deixe a animação rodar uma vez em silêncio; na segunda volta, um aluno narra cada etapa com o comando ou o botão que você acabou de usar.

**"Pense" do PR (4 min).** Individual. Esperado: o `toLowercase`, a pasta `node_modules/` e o "aaa", com **Request changes**. Peça a alguém que leia o comentário do `toLowercase` como o mandaria ao colega. Pergunte: "como o revisor descobre o `toLowercase`?". Esperado: rodando o "Como testar". "Na aula 6, vocês veem que nem o ESLint pega esse."

**Seção "Conflitos" (8 min).** Pergunte, com o gancho: "dois colegas corrigem a mesma frase do trabalho, cada um de um jeito. Qual fica?". Esperado: a que os dois combinarem, conversando. "O Git também não escolhe: ele para o merge e pergunta. Conflito se resolve conversando." Leia as marcas de "Conflito: duas mudanças na mesma linha" e pergunte o que é `HEAD`. Esperado: a branch em que você está, o "você está aqui" do `git log`. Depois, ao vivo no `lojinha-regras-conflito`, os três casos de "Conflitos na prática":

:::steps
1. Com a segunda conta, faça o merge do PR da `feature/preco-fone-a`.
2. Atualize o PR da `feature/preco-fone-b`: *This branch has conflicts that must be resolved* (o caso 2).
3. No seu clone: `git switch main`, `git pull`, `git switch feature/preco-fone-b`, `git merge main`. Leia a saída com o `CONFLICT` (o caso 1). O `git status` mostra o `produtos.js` e o `catalogo.json` como *both modified*.
4. No `produtos.js`, o VS Code mostra as marcas e os botões, traduzidos em "Resolvendo o conflito". Combine o preço em voz alta com quem "é a Ana" e use **Accept Current Change**.
5. O `catalogo.json` não se resolve à mão (o caso 3): `npm run catalogo` o grava de novo a partir do `produtos.js` resolvido, e prova que ele voltou a ser JavaScript válido.
6. `git diff --check` sem nada, `git add` nos dois, `git commit -m "Resolve conflito no preço do fone"`, `git push`; PR verde e merge.
:::

**Seção "Mensagens de erro" e "Resumo" (2 min).** Pergunte, com o gancho: "o Git também acende luzes no painel. Vocês sabem ler cada uma?". "A mensagem de erro é a luz do painel do carro, como no E02: diz o que aconteceu e onde." Em "Quando aparece um erro", pergunte quais a turma já viu hoje (o `Author identity unknown` e o `CONFLICT` costumam aparecer). Em "O erro mais comum: o push recusado", a frase que fica: "traga primeiro, envie depois; nunca `--force`". No resumo, volte às respostas anotadas no início: "salvar na nuvem" é o push; "cada um na sua cópia" é a branch, com PR para juntar.

:::tip Ritmo
Se atrasar, mostre "Mensagens de commit" sem perguntas, nos slides "na prática" sem demonstração aponte só o primeiro caso, e revise o PR do README sem o commit de correção. A mão na massa até o push, o PR ao vivo e o conflito ao vivo não se cortam: o laboratório repete os três.
:::

## Pausa (10 min)

Cada aluno adiciona o colega da dupla em **Settings**, **Collaborators**; o colega aceita em github.com/notifications. Confira por amostragem: no repositório do aluno, a aba **Collaborators** mostra o colega sem "Pending".

## Bloco 2 · Lint, formatação e depuração (50 min)

Faça as demonstrações no `lojinha-regras` do Bloco 1, numa branch `chore/qualidade`. Cada seção abre com o gancho do slide, que é a pergunta para a turma.

**"O que você vai aprender", "Palavras novas de hoje" e "A semana antes da entrega" (3 min).** Leia as cinco palavras novas, uma frase cada. Na pergunta, esperado: o `categria`, que o lint acha sem rodar. Escreva no quadro linter, formatador e depurador; eles ficam até o fechamento.

**Seção "O linter" (14 min).** Pergunte, com o gancho: "como o corretor do celular acha a palavra errada antes de vocês enviarem?". Esperado: ele confere cada palavra com as que conhece, sem precisar mandar. "O linter é o corretor ortográfico do código: lê sem rodar e sublinha o que parece erro." Ao vivo:

:::steps
1. `npm install -D eslint @eslint/js globals`. Em "Instalando o ESLint", abra o `package.json` e mostre as `devDependencies` novas ao lado do `picocolors`, em `dependencies`: "o relatório funciona sem o ESLint; ele é ferramenta de quem programa". A turma ainda não viu o `-D`: é a primeira vez.
2. Crie o `eslint.config.js` **sem** o bloco dos globais: só os imports de `@eslint/js` e `defineConfig` e a lista com `js.configs.recommended`. `npx eslint .`: 8 erros de `no-undef`, um para cada `console` e o `process`. O `npx` roda a ferramenta sem script; a turma o vê de novo no Prettier.
3. Pergunte: "o relatório roda; por que o ESLint acha que `console` não existe?". Esperado: ele não sabe que o código roda no Node. Acrescente o bloco do `globals.node` e o import de `globals`: nenhum erro. Leia "O eslint.config.js em português" linha por linha, apontando cada uma no código.
4. No `package.json`, à mão, `"lint": "eslint ."`; `npm run lint`: só o nome do script (o caso 2 de "O lint na prática").
5. No relatório, troque `categoria` por `categria` dentro do filtro e acrescente `import path from 'node:path';` no topo. A extensão sublinha e o Error Lens escreve a mensagem na linha (o caso 3). `npm run lint`: os 2 erros de "Rodando o lint", com a tradução das mensagens.
6. `npm run relatorio` roda; `npm run relatorio casa` quebra com `ReferenceError`. "Sem o lint, só descobre quem passar uma categoria." Desfaça.
7. O caso 1 de "O lint na prática": no `produtos.js`, repita `preco: 34.99` no fim da Garrafa Térmica e rode o lint: `no-dupe-keys`. Pergunte qual preço vale. Esperado: o último. Desfaça e passe por "As regras recomendadas".
:::

**"Pense" (4 min).** Duplas, 2 minutos. Esperado: `path` e `livro`; a média dividida por 12 passa. Pergunte quem acharia o terceiro. Esperado: o depurador ou um teste (E04).

**Seção "O formatador" (10 min).** Pergunte, com o gancho: "por que a escola pede o trabalho com a mesma fonte e a mesma margem?". Esperado: para todos lerem igual e ninguém discutir aparência. "O Prettier é a norma de formatação do código: muda a aparência, nunca o que o código faz."

:::steps
1. `npx prettier --check .`, ainda sem `.prettierrc`: o Prettier reclama, porque o padrão dele é aspas duplas.
2. `npm install -D prettier` e o `.prettierrc` do slide. `npx prettier --check .`: agora só o `produtos.js`, como no caso 1 de "O Prettier na prática".
3. Crie o `.prettierignore` com `src/data/catalogo.json`. Pergunte por quê. Esperado: quem escreve o JSON é o `npm run catalogo`.
4. `npx prettier --write .` (o caso 2: só o `produtos.js` sem *unchanged*) e `git diff --stat`: o `produtos.js` com uma propriedade por linha. "Por isso a formatação vai num commit só dela." `npx prettier --check .` de novo: a frase do caso 3.
5. `.editorconfig` e `.vscode/settings.json`. Bagunce o recuo do relatório e salve: tudo volta ao lugar.
:::

Da seção "O depurador" à seção "Os painéis", a demonstração é uma só (14 minutos ao todo).

**Seção "O depurador" (5 min).** Pergunte, com o gancho: "num replay de futebol, para que serve a câmera lenta com pausa?". Esperado: para ver o lance que passou rápido demais. "O depurador é a câmera lenta do programa: para numa linha e mostra cada detalhe daquele instante." Ao vivo, os três casos de "O depurador na prática":

:::steps
1. Cole o `src/scripts/preco-medio.js` do slide e rode num terminal comum: `Preço médio: R$ 181.98`. Leia "O preco-medio.js em português"; na `somar`, diga só a frase do slide: "uma função é uma receita com nome". Funções são do E07.
2. Em "Ligando o depurador": seta ao lado do `+` no terminal, **JavaScript Debug Terminal**. Rode de novo: `Debugger attached.` e a mesma média. "Ligado, mas sem pausa: falta dizer onde o filme para."
3. No `catalogo.json`, troque o `79.9` da Garrafa Térmica por `"79.90"`, entre aspas. Rode: `R$ NaN`. Pergunte: "o erro está na função ou no dado?". Anote os palpites.
:::

**Seção "Breakpoints" (5 min).** Pergunte, com o gancho: "onde vocês apertam o pause para ver o lance que importa?". Esperado: bem no lance. "O breakpoint é onde o filme pausa." Depois: "e se o lance que interessa é só um entre doze?". Esperado: pular direto para ele. "O condicional pausa só na cena que interessa."

## Dificuldades frequentes

| Sintoma | Causa provável | Como ajudar |
|---|---|---|
| `git push` recusado com `rejected` | O GitHub tem commits que a máquina não tem | `git pull`, resolver o conflito se houver e `git push`; nunca `--force` |
| `node_modules/` continua no `git status` | `.gitignore` criado com `echo` no PowerShell (UTF-16) ou fora da raiz | Apagar e criar pelo VS Code, na raiz, ao lado do `package.json` |
| `Author identity unknown` no commit | Máquina da escola sem `user.name` e `user.email` | Os dois `git config --global` do E01 |
| Aviso `LF will be replaced by CRLF` | O Git do Windows ajustando o fim de linha | É só aviso; o `"endOfLine": "auto"` impede o Prettier de reclamar |
| O colega não aparece em **Reviewers** ou não aprova | Convite não aceito, ou ele é o autor do PR | **Settings**, **Collaborators**; aceitar em github.com/notifications |
| Editor estranho no terminal depois do `git merge` | O commit de merge abriu o Vim | <kbd>Esc</kbd>, `:wq` e <kbd>Enter</kbd>; se for o VS Code, fechar a aba |
| `ESLint couldn't find an eslint.config.* file` | Arquivo com outro nome ou fora da raiz | `eslint.config.js` na raiz |
| `require is not defined in ES module scope` | Configuração copiada em CommonJS | `import` e `export default`, como no slide |
| `'console' is not defined` em todo script | Faltou o bloco do `globals.node` | Conferir o bloco e o `import globals from 'globals'` |
| O breakpoint nunca para | Script rodado num terminal comum, ou linha fora do caminho | JavaScript Debug Terminal; testar com um `debugger;` na linha |
| O script parece travado | Pausado num breakpoint esquecido | <kbd>F5</kbd> e remover todos no painel Breakpoints |
| Salvar não formata o arquivo | Extensão Prettier ausente ou outro formatador padrão | Instalar e conferir o `.vscode/settings.json` |
| `SyntaxError: Unexpected token '<<'` | Marcas de conflito no arquivo | Buscar `<<<<<<<`; `git diff --check` antes do commit |
| Projeto: o `git status` do `racha-conta` lista `produtos.js` e o `relatorio-catalogo.js` | `git init` rodado no `lojinha-regras`, ou `racha-conta` dentro dele | Conferir a pasta no prompt; mover o `racha-conta` para o lado e rodar o `git init` dentro dele |

## Plano B

- **Sem internet ou GitHub fora do ar:** o Git funciona sem rede. `init`, `.gitignore`, commits, branch, merge e conflito no próprio repositório, simulando as duas pessoas com duas branches locais. O push, o PR e a revisão ficam para casa; o quiz vai para a abertura do E04. ESLint e Prettier precisam do npm: hotspot em turnos de 4, ou o `node_modules` de uma máquina que instalou, copiado num pen drive.
- **Aluno sem acesso ao GitHub:** recuperação da senha ou da verificação em duas etapas na pausa; enquanto isso, ele faz os commits locais e revisa o PR do colega na tela dele. O push vai em casa.
- **Colega faltou:** trio em rodízio ou você como revisor. Para o conflito, dois clones do próprio repositório (`git clone <url> lojinha-2`), um para cada papel.
- **O depurador do VS Code não para:** rode `node --inspect-brk src/scripts/relatorio-catalogo.js Audio`, abra `chrome://inspect` no Chrome e clique em **inspect**: a aba Sources abre parada na primeira linha. - **Sem projetor:** grafo de branches no quadro a cada comando e demonstrações em grupos de 5 em volta do seu computador.
- **Turma atrasada:** o conflito em dupla (passo 7) já é da tarefa de casa.

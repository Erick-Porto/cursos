## Visão do encontro

**Objetivo:** o `lojinha-regras` passa a se conferir sozinho: Jest com Babel, os primeiros testes (`abreviar` e as categorias do catálogo), um ciclo de TDD (`boasVindas`), o script `verificar`, variáveis de ambiente com `process.env` e `--env-file`, e o GitHub Actions rodando lint e testes a cada push e PR. No bloco Projeto, o `racha-conta` ganha a primeira regra pelo TDD: a `calcularGorjeta`, etapa 3 do Projeto 1.

**Resultado ao fim das 4h:** 12 testes ou mais, `npm run verificar` sem erros, visto e selo verdes; o `.env` e o `.env.example` terminam em casa. No `racha-conta`, o Jest instalado e o primeiro teste da `calcularGorjeta` visto vermelho; o resto da etapa 3 termina em casa. É o último encontro da unidade Ambiente JavaScript: quem concluir as 8 aulas (E01 a E04) ganha a conquista **Primeiro script**.

**Pré-requisitos:** `lojinha-regras` do E03: `package.json` com `"type": "module"`, os scripts `catalogo`, `relatorio` e `lint` e o `picocolors` (E02); `eslint.config.js` com `@eslint/js` e `globals.node`, lint zerado (E03); repositório público no GitHub com `git push` funcionando e o fluxo de branch e PR do E03.

**A turma ainda não estudou a linguagem** (ela começa no E05). Hoje os alunos leem e copiam funções curtas, explicadas em uma frase; o foco é o que entra, o que sai e como conferir. Não detalhe o `if`, o `slice`, o `trim`, a arrow function `() =>` nem o `+` de textos: os slides dizem onde cada um volta (o `if`, as funções e a arrow function no E07; `slice` e `trim` no E06).

**Como os slides foram escritos:** para quem nunca programou. Cada aula abre com "Palavras novas de hoje", e todo código novo vem com a tradução logo abaixo ou num slide "... em português" (o primeiro teste e as duas partes do `verificar.yml`). As analogias são as do curso inteiro: o teste é uma prova com gabarito que o computador corrige sozinho, o Jest é o corretor e a integração contínua é a inspeção automática a cada entrega. Use as mesmas palavras em voz alta; não invente outra imagem para a mesma ideia.

**Slides de seção:** cada conceito vem em três slides. O primeiro, a seção, tem só o nome do conceito e uma frase de gancho, no centro ("O Jest" e "E quem aplica e corrige a prova do seu código?"). É a hora da conversa: leia o gancho, ouça duas ou três respostas e explique com a analogia indicada abaixo. O segundo explica o que é e como usar, por escrito; em aula, passe por ele apontando o que acabou de dizer, sem ler tudo. O terceiro, "... na prática", mostra dois ou três casos de uso com a saída: rode um deles ao vivo, ou mostre a saída no slide.

**Materiais:** projetor com terminal e navegador lado a lado, quadro, Wi-Fi, seu repositório de demonstração, o repositório vitrine (abaixo) e o quiz publicado.

## Abertura (15 min)

Retomada (5 min):

1. "O que o lint encontra que o Prettier não encontra?" Esperado: erros no código, como uma variável que não existe ou um import errado; o Prettier só arruma a forma.
2. "Como você para um script numa linha para ver o valor de uma variável?" Esperado: um breakpoint no VS Code, clicando à esquerda do número da linha, e o script rodando pelo depurador. Gancho: "O depurador ajuda a achar um bug que você já sabe que existe. Hoje vocês ganham algo que acha o bug antes de alguém ver."
3. "Por que a mudança entra por uma branch e um PR, e não direto na `main`?" Esperado: alguém revisa antes do merge e a `main` fica sempre funcionando. Gancho para o Bloco 2: "Hoje a revisão ganha um revisor automático."

Tarefa de casa (5 min): abra 2 repositórios do E03 e confira o `eslint.config.js`, `npm run lint` sem erros e o PR mesclado. Quem está sem lint instala agora (`npm i -D eslint @eslint/js globals`) e copia o `eslint.config.js` da solução de referência abaixo: o `verificar` de hoje depende dele.

Objetivos (5 min): projete "O que você vai aprender" da aula 7. "Hoje o `lojinha-regras` ganha um revisor que não cansa: ele roda os testes a cada push e avisa quando algo quebra." Avise: "Vocês vão ler funções prontas. O que importa hoje é o que entra e o que sai; cada parte do código vocês aprendem a partir do E05."

## Bloco 1 · Testes automatizados com Jest (50 min)

**"O que você vai aprender", "Palavras novas de hoje" e "O preço que sumiu" (4 min).** Leia as seis palavras em voz alta, com um exemplo rápido de cada. Conte a história do preço e faça a pergunta do slide. Esperado: as funções que mexem com dinheiro e as que recebem o que alguém digitou, porque aparecem em vários lugares e um erro nelas custa caro.

**Seção "Testes automatizados" (3 min).** Leia o gancho das 300 provas. Esperado: uma máquina que lê o cartão-resposta, ou o professor com o gabarito na mão. "Um teste automatizado é uma prova com gabarito que o computador corrige sozinho: a questão é usar a função, e o gabarito é o resultado que vocês esperam." Na âncora "Teste: uma prova com gabarito", aponte as três linhas da tabela e o exemplo do `abreviar`. Em "Testes automatizados na prática", os dois primeiros casos a turma já viveu: pergunte quem lembra do `Audio` do E02 e da média dos livros do E03.

**Seção "O Jest" (7 min).** Leia o gancho. Esperado: um programa. "É o Jest, o corretor." Em "Jest no lojinha-regras", instalação coletiva, cada aluno no próprio projeto; enquanto o npm baixa, leia a tabela do comando e o slide "npm test e o babel.config.json":

:::steps
1. `git status` limpo e o terminal do VS Code na raiz do `lojinha-regras`.
2. `npm i -D jest babel-jest @babel/preset-env`: os três entram em `devDependencies`, como o ESLint no E03.
3. `npm pkg set scripts.test=jest`: troca o `test` do `npm init` sem risco de vírgula errada. Abra o `package.json` e mostre a linha nova. "Lembram do `test` do E02, que só mostrava um erro? Hoje ele ganhou função."
4. Crie o `babel.config.json` na raiz, com a linha do slide. "O Babel é o tradutor: passa o `import` do projeto para o formato que o Jest lê."
5. `npm test`: "No tests found, exiting with code 1" é esperado. Ainda não há teste. É a resposta 1 de "O Jest na prática"; as outras duas a turma vê daqui a pouco.
:::

Quem não vê essa mensagem, você atende na pausa.

**Seção "Entrada e saída" (3 min).** Leia o gancho. Esperado: não; ele confere a resposta com o gabarito. "Para testar uma função, vocês só precisam saber o que entra e o que sai." Em "A função que você vai testar", crie `src/utils/texto.js` copiando o slide e leia as duas linhas da lista, sem detalhar o `if` nem o `slice`. Em "Entrada e saída na prática", peça a saída de cada linha antes de mostrar o comentário; a turma não cria o script de rascunho.

**Seção "O primeiro teste" (5 min).** Leia o gancho. Esperado: uma prova por função, uma questão por caso e a resposta certa como gabarito. "No Jest, o `describe` é a prova de uma matéria, o `test` é uma questão e o `expect` confere com o gabarito." Crie `texto.test.js` e rode: `Tests: 2 passed`. Leia "O primeiro teste em português" linha por linha, apontando cada uma no código; da arrow function, só a frase do slide. Em "O primeiro teste na prática", acrescente o teste das panelas e crie o `src/data/produtos.test.js` com o "são quatro": `Tests: 4 passed`. Pergunte: "Se amanhã alguém reescrever o `abreviar` de outro jeito, o teste muda?" Esperado: não; ele confere a promessa, não o jeito.

**Seção "Ler uma falha" (4 min).** Leia o gancho. Esperado: qual questão, a resposta certa e a que eu dei. "O Jest mostra a mesma coisa: o nome do teste, o Expected e o Received." Escreva o teste com `toBe('Caixa de Som…')`, colando o `…` de um documento (no Windows, <kbd>Alt</kbd> + <kbd>0133</kbd> no teclado numérico também produz o caractere). Rode, leia a falha na ordem do slide "Lendo uma falha" e pergunte: "Quem está errado, a função ou o teste?" Esperado: o teste, porque o comentário da função promete três pontos. É o caso 1 de "Falhas na prática". Mostre a linha marcada com `>`, corrija para `'Caixa de Som...'` e veja o verde. O caso 2, o código errado, a turma provoca de propósito na seção "Escolher os casos".

**Seção "Matchers" (4 min).** Leia o gancho. Esperado: a resposta exata, ter a palavra-chave, ter tantos itens. "O matcher é o jeito de corrigir." Comente `toBe`, `toEqual`, `toContain` e `toHaveLength`; o `toThrow` volta no E17. Em "Matchers na prática", mostre os dois testes do `texto.test.js` só pelo slide e troque, no `produtos.test.js`, o "são quatro" para `toHaveLength(4)`. Em "toBe ou toEqual?", acrescente o teste "a primeira é Áudio" e mostre o `toBe` falhando com `serializes to the same string`. A frase da analogia: "o `toBe` pergunta se é a mesma casa; o `toEqual`, se as casas são iguais por dentro". Troque por `toEqual`: verde.

**Seção "Arrange, act, assert" (3 min).** Leia o gancho da receita. Esperado: separar os ingredientes, cozinhar, provar. "São as três partes de todo teste: arrange, act e assert, preparar, agir e conferir." Escreva o teste "não passa do limite" e aponte os três comentários. "Arrange, act, assert na prática" fica para leitura; no caso 2, aponte só a lista pequena feita para o teste: o `filter` é a peneira do E02.

**Seção "Escolher os casos" (4 min).** Leia o gancho do elevador. Esperado: com 8, exatamente; alguém fala de 9 ou de nenhuma. "Esse é o caso de borda, e é nas bordas que os bugs se escondem." Em "Que casos testar", a tabela dos três tipos. Em "Vários casos com test.each", escreva a tabela. **Quebre o código de propósito**: troque `<=` por `<` no `abreviar` e rode. Vermelho na linha do limite exato, com `Received: "Fone Blueto..."`: é o caso 2 de "Falhas na prática", o código errado. Desfaça: é o hábito que separa teste de enfeite. Rode `npm test -- --verbose` para mostrar os nomes montados pelo `%p`.

**"Pense" (3 min).** Duplas. Esperado: a tabela da resposta, com a borda dos espaços. Se surgir o nome vazio, anote no quadro como pergunta para a dona da loja: "Teste também serve para descobrir regra que ninguém decidiu."

**Seção "TDD" (6 min).** Leia o gancho e emende: "no Pense, foi o que vocês fizeram: os casos vieram antes da função". Esperado, para a pergunta "que vantagem tem?": dá para saber na hora se a função acertou. "TDD é escrever o gabarito antes de resolver a questão." Em "TDD: o teste vem antes", deixe a animação do ciclo rodar uma volta e aponte a seta do próximo teste. Os três slides seguintes são o TDD na prática e acompanham a demonstração ao vivo, no `texto.test.js`:

:::steps
1. Escreva no quadro os três casos do Pense.
2. Importe o `boasVindas`, escreva o teste do `'Ana'` e rode: vermelho, `boasVindas is not a function`.
3. Verde mínimo: a função com `'Olá, ' + nome + '!'`. Verde.
4. Escreva o teste do `'  Ana '` e peça palpites do Received antes de rodar: vermelho, `"Olá,   Ana !"`. Compare com os palpites.
5. Acrescente o `.trim()`: os dois testes verdes.
6. Refatore os dois testes numa tabela do `test.each` e acrescente a linha do `'Ana Souza'`: três verdes. A frase do refatorar: "passar a receita a limpo, com palavras melhores, sem mudar o bolo".
:::

**Seção "Cobertura" (2 min).** Leia o gancho do marca-texto. Esperado: que ninguém leu aquela página. "A cobertura é o marca-texto dos testes." É "Cobertura na prática" ao vivo: comente o `describe` do `boasVindas` e rode `npm test -- --coverage`: `% Funcs` cai para 50 e a linha 8 aparece na coluna Uncovered. Abra `coverage/lcov-report/index.html` no navegador: a linha sem teste fica em vermelho. Volte o `describe` e rode de novo: 100 nas quatro colunas. Em "100% não quer dizer sem bug", pergunte: "100% quer dizer sem bug?" Esperado: não, só que toda linha rodou.

**Seção "Mensagens de erro", "Resumo" e "Próximos passos" (2 min).** Leia o gancho das luzes do painel e a tabela de erros: a maioria já apareceu ao vivo. O resumo em voz alta.

:::tip Ritmo
Se atrasar, pule o relatório HTML da cobertura e deixe "Matchers na prática" e "Arrange, act, assert na prática" só para leitura. A instalação, a leitura da falha e o TDD não se cortam: o laboratório usa os três.
:::

## Bloco 2 · Automação e integração contínua (50 min)

**"O que você vai aprender", "Palavras novas de hoje" e "Funciona na minha máquina" (4 min).** Leia as palavras novas. Conte a história e faça a pergunta do slide. Esperado: um servidor que rode os testes a cada push e uma regra que exija verde para o merge.

**Seção "O script verificar" (8 min).** Leia o gancho. Esperado: chave, carteira, celular. "O `verificar` é um contato salvo que faz duas conferências em fila: o lint e os testes." Ao vivo: acrescente `"verificar": "eslint . && jest"` no `package.json` e rode `npm run verificar`. O lint para em `'describe' is not defined` e os testes nem aparecem: é o `&&` trabalhando. Em "O && e o código de saída", mostre o código `1` com `echo $?` (Git Bash) ou `$LASTEXITCODE` (PowerShell): "é o joinha do programa; `0` é deu certo". Leia os três casos de "O verificar na prática": a turma está no caso 2, com outro erro de lint. Em "O lint precisa conhecer o Jest", acrescente o bloco do `globals.jest` no `eslint.config.js` e rode de novo: tudo verde, saída `0`, o caso 1.

**Seção "Variáveis de ambiente" (5 min).** Leia o gancho do Wi-Fi. Esperado: porque cada casa tem o seu Wi-Fi, com outro nome e outra senha. "Variável de ambiente é o Wi-Fi da casa: o código é o mesmo, a configuração muda de lugar para lugar." Crie `src/scripts/ambiente.js` e rode com `node`: `API: undefined`. Em "O arquivo .env", crie o `.env` ("o papel na geladeira com a senha do Wi-Fi") e rode com `--env-file=.env`: aparece o endereço. Rode com `--env-file=.env.local` para mostrar o `not found`. Crie o script `ambiente` no `package.json` e rode `npm run ambiente`: é o caso 3 de "Variáveis de ambiente na prática". O caso 1, duas máquinas, fica no slide.

**Seção "Segredos" (4 min).** Leia o gancho. Esperado: não. "O repositório é público como uma rede social: senha, token e chave ficam só no `.env`." Mostre o `git status`: o `.env` aparece até entrar no `.gitignore`, junto com `coverage/`. Em "Segredos na prática", leia os três casos; o do app, o `EXPO_PUBLIC_`, é só prévia do E30: fale dele em uma frase. Em ".env.example e .gitignore", crie o `.env.example`: "o modelo do papel, com os nomes e sem as senhas". "O endereço da DummyJSON é segredo?" Esperado: não; a regra vale para senhas, tokens e chaves.

**Seção "Integração contínua" (3 min).** Leia o gancho da fábrica. Esperado: a inspeção, o controle de qualidade. "Integração contínua é a inspeção automática a cada entrega, e o GitHub Actions é o inspetor." Desenhe no quadro: push, runner Linux novo, `npm ci`, `eslint .`, `jest`, visto ou X. O desenho fica até o laboratório. Em "As peças do GitHub Actions", o runner é "uma bancada nova e vazia a cada inspeção". Projete "Do push ao visto verde" e pergunte: "se o lint falhar, o `jest` roda?" Esperado: não; o `&&` para no primeiro erro, o passo fica vermelho e o resultado é o X. Em "Integração contínua na prática", pergunte qual linha da tabela teria salvo a dupla da terça. Esperado: a primeira.

**Seção "O workflow" (8 min).** Leia o gancho do inspetor. Esperado: quando conferir, em que máquina, quais passos. "O workflow é esse bilhete, escrito em YAML." Leia "verificar.yml (1) em português" e "(2) em português" apontando cada linha no código. Antes do push, projete "O workflow na prática" e pergunte, linha por linha, "roda?". No `lojinha-regras` de demonstração:

:::steps
1. `git switch -c feature/testes-e-ci`.
2. Crie `.github/workflows/verificar.yml` com as duas partes dos slides; mostre a pasta com ponto no VS Code.
3. Selo no topo do `README.md`, com o seu usuário.
4. Commit "E04: testes e CI" e `git push -u origin feature/testes-e-ci`.
5. Abra o PR: o check "Verificar / verificar" aparece amarelo.
6. Na aba Actions, abra o job e os passos enquanto rodam. A primeira execução leva de 1 a 3 minutos.
:::

**Seção "npm ci" (2 min).** Enquanto o Actions roda. Leia o gancho do mercado. Esperado: pela nota fiscal. "O `npm ci` instala exatamente o que diz a nota fiscal, o `package-lock.json`; se ela não bate com a lista de ingredientes, ele para em vez de consertar." Aponte a tabela `npm install` x `npm ci`. Em "npm ci na prática", o caso 1 é o atalho para quem ver um X no laboratório: `npm ci` e `npm run verificar` no próprio computador.

**"Pense" (3 min).** Esperado: o runner só tem o que está no Git, e o lock antigo não tem o pacote novo; o `npm ci` não conserta o lock, e a correção é o commit do `package-lock.json`.

**Seção "Ler o resultado" (4 min).** Leia o gancho do delivery. Esperado: pelo status do pedido no app. "O GitHub mostra o status da inspeção: amarelo, verde ou X." Volte ao PR: visto verde. Faça o merge e mostre a execução na `main` disparada por ele; ao terminar, o selo do README fica verde: "é o selo de vistoria do projeto". O caminho de "Ler o resultado na prática" a turma vê no PR quebrado, na próxima seção.

**Seção "Proteger a main" (4 min).** Leia o gancho do metrô. Esperado: a catraca. "A regra de proteção é a catraca: o PR só passa com o visto verde." No repositório vitrine, abra o PR `demo/quebrado`: X vermelho e "Merging is blocked". Faça o caminho de "Ler o resultado na prática": **Details**, passo **Lint e testes**, e leia com a turma a falha do limite exato, Expected `"Fone Bluetooth"`, Received `"Fone Blueto..."`. Mostre a regra em Settings > Branches: opcional no `lojinha-regras`, obrigatória em equipe. Em "A proteção na prática", leia a mensagem do push recusado; não a provoque ao vivo.

**Seção "Mensagens de erro", "Resumo" e "No laboratório" (2 min).** Leia o gancho das luzes do painel e faça uma leitura rápida da tabela de erros e do resumo.

**Desafio que prepara o laboratório (3 min).** Em duplas: "Listem os arquivos que vocês vão criar ou mudar e se cada um vai para o Git." Esperado: vão `texto.js`, `texto.test.js`, `produtos.test.js`, `ambiente.js`, `package.json`, o lock, `babel.config.json`, `eslint.config.js`, `.gitignore`, `.env.example`, `verificar.yml` e `README.md`; ficam fora `.env`, `coverage/` e `node_modules/`. A lista no quadro vira o checklist.

:::tip Ritmo
Se atrasar, só cite o `not found` do `--env-file` e leia "Segredos na prática" sem comentar. O workflow ao vivo e o PR bloqueado não se cortam; se o Actions demorar, siga para o "npm ci" e o "Pense" e volte ao PR depois.
:::

## Laboratório (55 min)

**Enunciado:** os passos do slide "No laboratório" da aula 8, com o checklist do quadro, menos o passo 4: o `.env`, o `.env.example` e o `.gitignore` vão para a tarefa de casa. A turma viu os três ao vivo no Bloco 2, e o E05 não depende deles. Assim sobram os 15 minutos do projeto.

**Organização:** individual, na branch `feature/testes-e-ci`. A dupla do desafio revisa o PR do colega, como no E03, e só aprova com o check verde.

**Marcos:** 2:30, Jest rodando e os testes do `abreviar`; 2:45, `boasVindas` pelo TDD e 12 testes verdes; 2:55, `verificar` verde; 3:05, PR aberto com o check rodando; 3:15, merge, visto verde e entrega.

**O que observar:** `toBe` com objeto; reticências ou aspas copiadas de documento; `import` sem o `.js` no fim, que o Jest aceita e o `node` recusa; teste que depende do `.env`; `.env` em **Files changed**; YAML com tab; pasta `github` sem ponto; lock fora do commit; `jest --watchAll` copiado de tutorial; `npm audit fix --force`, que rebaixa o Jest. Para todo teste novo: "Você já viu esse teste vermelho?"

**Para quem termina cedo:** 100% em todas as colunas da cobertura do `texto.js`, ou a regra de proteção na própria `main`, provada com um PR quebrado.

## Dificuldades frequentes

| Sintoma | Causa provável | Como ajudar |
|---|---|---|
| "No tests found, exiting with code 1" | Nenhum arquivo termina em `.test.js` (por exemplo, `.teste.js`) | Conferir o nome; `npx jest --listTests` lista o que o Jest achou |
| `Must use import to load ES Module` ou `Cannot use import statement outside a module` | `babel.config.json` ausente, com outro nome ou fora da raiz | Conferir nome e local; o arquivo fica ao lado do `package.json` |
| `TypeError: ... is not a function` | Nome importado diferente do exportado, ou função sem `export` | Conferir a grafia no `import` e o `export` no `texto.js` |
| Expected e Received quase iguais | Reticências (`…`) ou aspas curvas copiadas de um documento | Redigitar o esperado no VS Code |
| Lint com `'describe' is not defined` | `eslint.config.js` sem o bloco dos testes ou com `files` errado | Colar o bloco do slide, com `'**/*.test.js'` |
| Lint com `'globals' is not defined` | Config sem o `import globals from 'globals'` do E03 | Import no topo e `npm i -D globals` |
| `API: undefined` | Script rodado sem `--env-file`, `.env` fora da raiz ou nome da variável diferente | `npm run ambiente`; conferir `API_URL` nos dois lados |
| `node: .env: not found` | Clone novo, sem o `.env` | `cp .env.example .env` (no Prompt de Comando, `copy`) |
| Push recusado: "refusing to allow a Personal Access Token to create or update workflow" | Token sem o escopo `workflow` | Novo token com `workflow`, ou novo login pelo Git Credential Manager |
| Nada aparece na aba Actions | Pasta `github` sem ponto, `workflow` no singular ou arquivo em outra branch | Caminho `.github/workflows/verificar.yml`, na branch do push |
| "Invalid workflow file" | Tab ou indentação errada no YAML | Reindentar com espaços; "Render Whitespace" no VS Code mostra os tabs |
| `npm ci` vermelho: "package.json and package-lock.json are in sync" | Lock fora do commit ou desatualizado | `npm install` local e commit do `package-lock.json` |
| `npm audit` aponta vulnerabilidade no Jest e sugere `--force` | Dependência antiga de uma ferramenta que só roda no computador | Não use `--force`: ele rebaixa o Jest para a versão 25 e quebra os testes |
| Projeto: `npm test` no `racha-conta` diz "Error: no test specified" | O `test` do `npm init` continua no `package.json` | `npm pkg set scripts.test=jest` |
